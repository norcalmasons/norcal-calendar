# Regional authorization migration

## Stage 1 — ownership foundation (NorCal Dev only)
Five division records; migrated test records belong to Division IV. Only IV is currently onboarded; all owned tables and staff assignments have temporary IV-only database gates. Existing legacy roles still drive the deployed application. The new regional role metadata is not an active authorization system. Existing enabled organizational administrator maps to system_admin; disabled legacy admins map to division_admin; disabled legacy inspectors map to inspector. Newly created legacy staff have no regional role until explicitly assigned.

## Required before lifting gates
- Central server-side authorization using verified Auth identity, enabled staff record, MFA AAL2, explicit regional role and division membership; no reliance on client-supplied scope or user metadata.
- System admin: all divisions; division admin: own division management; inspector: own division event approval/edit/cancel, bulk import and authorized document access. District is directory metadata, not an authorization boundary.
- Scope every read and mutation, including request approval RPCs, histories, corrections, staff management, bulk import and storage paths. Derive ownership of linked rows on server, reject mismatches. Public approved events can be read across onboarded divisions. Preserve independent lodge scheduling/verification terminology.
- Ensure no legacy unrestricted service-role handlers remain deployed before lifting IV-only checks. Remove implicit IV defaults from scoped writes once explicit ownership is implemented.
- Test cross-division read/write denials, AAL1 denial, disabled staff denial, system admin access and public approval filtering before onboarding new divisions.
- Review one unmatched event district string; do not silently correct. Queue/history rows use parent ownership; orphan or global rows need explicit treatment. Newsletter subscription selections, consolidated digests, division calendar mapping and AWS SES are separate later migrations. All outbound integrations remain disabled.
- Cutover: update auth site/redirect URLs and both hosted email templates' logo URL to production, PWA configuration and public safeguards only after approval. Division IV production untouched; redirect is separate decision.

## Stage 2A — centralized authentication and transitional lock
All seven privileged handlers import `supabase/functions/_shared/regional-auth.mjs`. The shared code validates the bearer with Supabase Auth, confirmed email, current enabled/nonremoved staff record, explicit matching regional role, and verified MFA factor + AAL2/sub claims. Unscoped legacy routes intentionally accept only system administrators. Other roles cannot be granted working access until their queries and mutations are scoped. Existing public config and original-submitter identity paths remain separate. No migration gates have been lifted. Unit policy and mocked identity tests are included in `tests/regional-auth-smoke.mjs`. Live browser/auth verification is required after deployment; no cross-division endpoint testing is possible with the IV-only gates in place.

## Stage 2B — lodge and correction management
These two handlers permit verified system admins or an enabled, onboarded division admin. All private lists and parent ID lookups use server-derived division scope; edits recheck role and division inside the database transaction. Lodge district selection is validated dynamically against the lodge's own division. Correction audit insertion is atomic with the status change. Public correction submission remains blocked, and all eight IV-only gates remain intact. Other five privileged handlers retain the system-admin-only transitional lock. Historical audit actor display names are retained for authorized parent records. No division admin accounts were enabled. Browser and eventual cross-division end-to-end tests remain required.

## Multi-division staff assignments
Canonical memberships are now `staff_division_assignments` (one row per account and division, with role and optional district). The account-level role is legacy compatibility only, except for system administrators. Non-system legacy regional roles are cleared so old unscoped bundles fail closed. Staff administration remains system-admin-only until safe scoped delegation is implemented; assignments can be entered for any of the five divisions but access is available only to onboarded divisions and only within converted handlers. Existing system administrators cannot be disabled or demoted through the staff editor; creating new system admins is a separate operation. Lodge/correction admin scope uses the intersection of admin memberships and onboarded divisions, with database-side rechecks. Inspector/event, resources, notification and other remaining handler conversions are pending. Do not lift the eight existing migration gates yet.

## Expansion requirement
The staff form and membership validation use the division directory dynamically, with no fixed five-division limit. The Office free-text input is removed; legacy metadata is preserved and not used for authorization. New divisions must be configurable by a system administrator through a future Divisions & Districts management screen, with unique ID/name/order, district and lodge directory setup, assignments, per-division calendar mapping and newsletter selection. Public menus, home rows, calendar filters and notifications must enumerate onboarded divisions from the database, not a hardcoded list. Activation must remain explicit after configuration and testing; current IV-only gates remain until the regional handlers are fully converted. Do not create additional divisions or activate them merely to test expansion outside rollback-only tests.

## Directory management implementation
System administrators can now add divisions and districts and edit display names/order through Administration → Divisions & Districts. All changes are audited in `division_directory_history`; division IDs and district codes are immutable in this UI, no deletion or activation is offered. The district-only migration gate was removed to permit advance directory preparation; seven other gates remain, including lodges, events, requests, and legacy account scope. New divisions are created with onboarded=false regardless of supplied values. Staff assignment selectors use the same database directory. Calendar mapping, newsletter settings, lodge import/setup, public filters and final activation are still pending. Do not assume the legacy event form's hardcoded district list is converted.

## Stage 2C — event mutation database authorization
Existing RPC signatures preserved so the currently deployed system-admin-only event handler remains compatible. Approval, rejection/correction decisions, inspector request edits, published-event edits, cancellations through approval, calendar retry and administrator undo now check the locked parent record's division against current enabled/nonremoved staff membership and onboarded division. Undo requires a division administrator membership for that same division or a system administrator. New approvals explicitly inherit division ownership from the request. District validation and title resolution are directory-driven; lodge abbreviation lookup is division-scoped. The six mutation RPCs now use SECURITY INVOKER; all nine new/updated routines are service-role-only. Rollback tests passed for same-division inspector approval/edit/cancel, wrong-division denial, invalid district denial, undo denial for a mixed-role account whose admin membership is in another division, and division school title generation. Confirmed 46 events, 49 requests, one enabled staff account and zero pending calendar/email jobs after rollback. Existing unmatched district 201 on a migrated virtual meeting was not reclassified; a later edit will require a valid district in its owning division. No gates lifted. Remaining event work: server-side read/query filtering including dashboard, audit and history, submissions and assignment-specific MFA routing, regional preview/title selection, bulk import and notification recipient routing, frontend division selection, and browser/end-to-end tests. Legacy global settings and title preview are not yet fully converted. No new divisions activated.

## Stage 2D — scoped event gateway
Private dashboard, requests, event details, list, sync overview and audit queries derive permitted onboarded divisions via regional_event_divisions, with optional validated division_id query selection. Private security-invoker read views exclude inconsistent parent history. Event mutation routes preflight the selected division and use the existing database-side actor rechecks. New submissions choose an authorized division (explicit when multiple are available); change/cancel requests inherit the target event's division. New request codes use DIV<id>. Reviewer notifications for ordinary submissions target active nonremoved assigned staff of that division only, not unrelated staff; bulk import routing remains legacy. Legacy system-admin-only login gateway remains deliberately closed to ordinary inspectors. Public submissions and outbound delivery remain disabled. Public config and frontend title preview are not yet converted, nor are bulk import and other legacy endpoints. Partial change validation uses the current published event when the inspector's patch omits district/type. Database read tests used rolled-back Division I membership and matched original dashboard output. Live HTTP/authenticated browser testing is pending.

## Stage 2E — saved lodge venues and atomic regional imports
Lodge directory adds nullable venue_name, address_line2 and validated zip_code; existing locations remain unchanged. Administrator edit uses the same optimistic lock and audit trail. The importer fills all location fields from a known lodge only when the venue/address fields are blank (a supplied ZIP may supplement the saved location). Missing ZIP remains a validation error, not an invented value. Actual approved New Events workbook was reopened and checked: headings match the parser, examples are rows 7–9, entry heading row 11, allowed entry rows 12–36. The importer submits via regional_bulk_submit, which rechecks per-row membership and directory ownership, groups rows by division, creates separate division-owned batch records and per-division reviewer summaries, and commits all writes in a single transaction. Identical retries replay batch results; unconfirmed duplicate rows are skipped. Only bulk_event_imports' temporary IV-only constraint/default was removed; event_requests and other migration gates remain. Rollback tests: venue save and bad ZIP rejection, mixed batch ownership (Division IV submitted + Division I skipped), replay, and atomic rollback on an attempted non-IV request blocked by the retained gate. No test records persisted. Deployed division-lodges v5 and division-bulk v4. Existing inspector/MFA development gate remains. Browser QA still required using the actual workbook; full non-IV submissions remain blocked until event ownership gates are lifted at cutover. Existing ZIP codes and venue names require directory completion. No external email/calendar jobs sent.
